# Цель и смысл

Данный документ описывает программный интерфейс двух веб–служб:

- TV Guide, также известный как "программа телепередач"
- Peers.TV, позволяющий смотреть записи телепередач и эфир каналов

Службы имеют общую предметную область, поэтому передаются с использованием одинаковой схемы данных.

С помощью данного API у обоих служб можно выяснить:

- название, описание канала
- текущую телепередачу для канала
- расписание выпусков телепередач (привязанное к территории)
- описание выпусков телепередач
- идентификаторы: каналов, телепередач и выпусков телепередач

TV Guide предоставляет меньше информации. Так, в нем не содержится информации:

- об адресах вещания каналов
- наличия записей телепередач для каналов и телепередач
- о ссылках на записи телепередач (ни magnet, ни HTTP, ни HLS, никаких)

В рамках службы Peers.TV можно получить всю указанную выше информацию.

На замену настоящему API для получения информации о каналах, телепередачах и выпусках готовится [Catalogue API][catalogue-api-ref], плановый срок релиза – июнь-июль 2014, поэтому для новых разработок рекомендуется ориентироваться на новый API.

[catalogue-api-ref]: catalogue.md?h=catalogue

Получение ссылок на адреса вещания разбивается на две отдельные сущности:

- Адреса вещания каналов. Приложение формирует список доступных адресов вещания каналов на основе доступных ему списков вещания каналов, предоставляемых различными контрагентами. Списки каналов обычно поставляются в XSPF или M3U форматах.
- Адреса вещания записей выпусков телепередач. Для этого разработана и внедрена служба Media Locator, работающая по одноименному протоколу: [Media Locator API][media-locator-api-ref]. 

[media-locator-api-ref]: media-locator.md

## Рубрикатор <span style="color:#f00">\[только в Peers.TV\]</span> [ch-rubricator]

Начиная с версии 2.8 в сервис Peers.TV введено понятие рубрикатора. Рубрикатор служит для формирования выборок выпусков телепередач или их фрагментов при навигации пользователем по меню приложения или схожим по функциональности с ним элементам графического интерфейса.

Рубрикатор является деревом предустановленных сервером фильтров, каждый фильтр при этом называется рубрикой, может иметь параметры, задающие особые параметры фильтрации множества выпусков телепередач и, возможно, изменение сортировки в выдаче.

**Внимание**: В сервисе Peers.TV риложение может осуществить выборку выпусков телепередач только с помощью рубрикатора. Других способов построить выборку сервис не предоставляет.

Рубрикатор может быть различным в зависимости от:

- приложения и его версии,
- устройства, на котором запущено приложение,
- территории,
- или контрагента, в сети которого запущено приложение.

Пример рубрикатора:

1. "Популярное", опции:
	- "Выборка". Возможные значения: "за неделю", "за все время"
	- "Сортировка". Возможные значения: "по новизне", "по количеству просмотров"
2. "Подборки", с подпунктами:
	1. "Чемпионат мира по хоккею"
	2. "Чемпионат мира по снукеру"
3. "Рекомендации"
4. "Поиск", опции:
	- "Поисковая строка", вводится пользователем

Тот же рубрикатор для устройств с пультом дистанцинного управления может выглядеть так:

1. "Популярное", с подпунктами:
	1. "За неделю"
	2. "За все время"
2. "Подборки", с подпунктами:
	1. "Чемпионат мира по хоккею"
	2. "Чемпионат мира по снукеру"
3. "Рекомендации"
4. "Поиск", опции:
    - "Поисковая строка", вводится пользователем

### Структура рубрикатора

Рубрикатор представляет собой дерево, узлы в котором называются рубриками. При выборе пользователем рубрики может быть осуществлена фильтрация множества выпусков телепередач.

Каждая рубрика может иметь подрубрики, а также опции, задающие дополнительные параметры выборки выпусков телепередач: сортировку или фильтрацию.

Опции возможны двух типов:

1. Переключаемые. В каждый момент времени пользователь должен выбрать одно из предлагаемых сервером значений. Одно из значений должно быть помечено как значение по умолчанию.
2. Требующие пользовательский ввод. Приложение должно отобразить пользователю поле для ввода значения опции.

*Рубрики первого уровня* (не являющимися подрубриками никакой другой рубрики) могут быть использованы для построения главного меню приложения, или разнесены по другим графическим элементам интерфейса. Так, роль главного меню в iOS может выполнять TabBar, при этом элемент поиска обычно располагается в верхней части интерфейса.

Рубрика может содержать дополнительную подсказку `ui_hint` о том, как отображать результаты выборки в приложении. Это также может помочь приложению реализовать ожидаемое поведение для имеющихся элементов графического интерфейса.

Например, представление в интерфейсе приложения выборок "Популярное" и "Рекомендации" могут отличаться по количеству отображаемой информации о выпусках телепередач, а выборка "Поиск" требовать отображения дополнительного всплывающего окна.

### Получение и интерпретация рубрикатора [para-rubricator-interpret]

Построение связи между графическим интерфейсом пользователя и рубрикатором должно производится по следующему алгоритму:

1. Отображается интерфейс пользователя.
2. Отправляется [запрос `rubricator`][m-rubricator] на получение рубрикатора.
3. Для каждой рубрики первого уровня подбирается подходящий элемент графического интерфейса. Соответствие осуществляется на основе подсказки `ui_hint`, указанной в рубрике.
	1. Если подходящий элемент графического интерфейса приложения не был найден, рубрика игнорируется как неподдерживаемая.
4. Если для какого-то элемента графического интерфейса не была найдена подходящая рубрика первого уровня, данная функциональность должна либо не отображаться, либо отображаться как недоступная на данный момент.
5. Приложение запоминает построенную иерархию рубрикатора:
	1. Либо до времени, указанного в HTTP заголовке `Expires` ответа сервера,
	2. Либо до смены одного из параметров: контрагента, территории, версии приложения,
	3. Иначе на 8 часов, после чего попытается обновить информацию с сервера.

Получение или обновление рубрикатора с сервера и связывание его с имеющимися элементами графического интерфейса должно производиться в фоновом режиме и не влиять на работу остальной функциональности приложения. При этом допускается отображать надпись "Производится загрузка информации" или ей подобную для выбранных пользователем элементов графического интерфейса, для которых ожидается рубрика с сервера, но в данный момент получение и построение рубрикатора еще не завершено.

Параметр `ui_hint` должен быть задан у рубрик первого уровня. Подрубрики наследуют это свойство от вышестоящей рубрики, если не указано обратное.

### Обработка выбора пользователем рубрики [para-get-for-rubric]

При выборе пользователем (переходе на пункт меню, нажатие на элемент графического интерфейса и т.п.) рубрики приложение:

  1. Для всех опций выбранной рубрики:
		1. Если опция имеет идентификатор, не встречающийся у вышестоящих рубрик, выставляется значения по умолчанию.
		2. Если опция имеет идентификатор, встречавшийся у рубрики уровнем выше, выставляется значение, выбранное на предыдущем экране.
  3. Если это предусмотрено в дизайне, опции отображаются в графическом интерфейсе.
  2. Все подрубрики отображаются согласно дизайну приложения.
  3. Если это не предусмотрено в интерфейсе приложения, следующее действие может не производиться, если у выбранной рубрики имеются подрубрики.
  4. С помощью [метода `telecasts`][m-telecasts] производится выборка списка выпусков телепередач рубрики. Полученные выпуски телепередач отображаются согласно дизайну для соответствующего значения `ui_hint`.

При изменении значения любой опции происходит переполучение списка выпусков телепередач для выбранной рубрики, с последующим обновлением интерфейса приложения в соответствии со значением поля `ui_hint`.

Если это предусмотрено интерфейсом, для опций, требующих ввод, пользователю предлагаются возможные продолжения ввода, с помощью [метода `suggest`][m-suggest].

Из описанного алгоритма вытекают следующие ограничения:

1. Различные рубрики не могут иметь одинаковых идентификаторов.
2. Различные опции (с различным набором значений, различными заголовками значений) не могут иметь одинаковых идентификаторов.
3. Опции могут иметь одинаковые идентификаторы тогда и только тогда, когда выполнены все условия:
	1. Совпадают типы опций,
	2. Совпадают множества значений,
	3. Для одинаковых значений используются одинаковые заголовки, отображаемые в интерфейсе,
	4. Совпадает значение по умолчанию,
	5. Рубрика, в которой используется повторный идентификатор опции, является подрубрикой рубрики с полным описанием опции
4. Для ссылки на опцию вышестоящей рубрики на сервере может быть указан только идентификатор опции, на которую дается ссылка.
5. Некорректные рубрики и опции должны быть проигнорированы приложением.

Рассмотрим для примера следующий рубрикатор:

- Рубрика "Интересно посмотреть",
	- опции:
		- переключаемая опция "сортировка", идентификатор `1`, значения: "по количеству просмотров" (выбрана по умолчанию), "по дате выхода"
	- подрубрики:
		- Рубрика "Украина",
			- опции: с идентификатором `1`
			- подрубрики: нет
		- Рубрика "Чемпионат мира по снукеру 2014",
			- опции: с идентификатором `1`
			- подрубрики: нет
- Рубрика "Рекомендации"
	- опции: 
		- переключаемая опция "жанр", идентификатор `2`, значения: "все" (выбрана по умолчанию), "фильмы", "мультфильмы"
	- подрубрики: нет

В данном случае подрубрики "Украина" и "Чемпионат мира по снукеру 2014" имеют одинаковую с вышестоящей рубрикой опцию "сортировка". При этом, если пользователь на экране рубрики "Интересно посмотреть" выбрал сортировку по дате выхода, она сохраняется и при переходе в подрубрики. Если способ сортировки в подрубрике был изменен, он должен быть изменен и в вышестоящей рубрике, а список выпусков получен заново.

Заметим, что наличие для рубрики "Рекомендации" опции с идентификатором `1` было бы ошибкой и 
было бы игнорировано приложением.

### Передача значений выбранных опций рубрик [para-rubric-options-encoding]

Параметры для методов [`telecasts`][m-telecasts] и [`suggest`][m-suggest] передаются следующим образом:

1. Числовой идентификатор выбранной рубрики, в параметре `rubric`.
2. Выбранные значения опций — в параметре `rubric_options`, при этом кодируются следующим образом:
	1. Для каждой опции формируется строка, содержащая ее числовой идентификатор и через символ `,` — выбранное значение.
	2. Для переключаемых опций значение передается в поле `value`, для опций требующих ввод, используется введенная пользователем строка в кодировке UTF-8.
	3. Все вхождения в выбранное значение символов `,`, `;` и `\` должны быть экранированы символом `\`, т.е. заменены на последовательности символов `\,`, `\;` и `\\`, соответственно.
	4. Все полученные строки конкатенируются через разделитель `;`.

При обработке метода `telecasts` сервер с помощью переданного параметра `rubric` определяет запрос, который необходимо выполнить в базе данных, а параметры запроса формирует из параметра `rubric_options`:

1. Параметр `rubric_options` декодируется с помощью функции `urldecode` (PHP) или аналогичной.
2. Массив значений получается путем разбивания полученной строки разделителем `;` (последовательность `\;` при этом не считается разделителем). 
3. Полученный массив преобразуется в ассоциативный массив с помощью отделения ключа от значения символом `,` (последовательность `\,` при этом разделителем не является).
4. Последовательности символов `\\`, `\,` и `\;` заменяются на символы `\`, `,` и `;`, соответственно.

Продолжая пример с iPhone приложением, при выборе пользователем рубрики "Популярное" приложение должно отправить [запрос `telecasts`][m-telecasts] с параметрами `rubric=1` и `rubric_options=100%2Сtoday`, так как значением опции "Период" с идентификатором `100` по умолчанию является "За сегодня", что и будет отображено в интерфейсе:

![](img/peerstv-iphone-menu-options-example.png?p=plain&h=TVREC-274)

Для передачи значений `one,two` для опции с идентификатором `1000` и `zero;first\\` для опции с идентификатором `1001` будет использована следующая строка:

	1000,one\,two;1001,zero\;first\\\\

Или в кодированном варианте:

	rubric_options=1000%2Cone%5C%2Ctwo%3B1001%2Czero%5C%3Bfirst%5C%5C%5C%5C

### Особенности реализации постраничной выдачи списка выпусков телепередач [para-paging-problem]

Каждая рубрика задает фильтр, SQL запрос, переданные значения опций позволяют данному запросу иметь несколько дополнительных параметров, влияющих на выборку или упорядочивание ее результатов.

При этом с течением времени результаты работы могут быть изменены: в ней могут появиться новые выпуски телепередач, удалиться старые. При этом приложение может запросить результаты со "следующей страницы" выдачи, не желая при этом получать дубликаты выпусков телепередач.

Рассмотрим классический пример постраничной выдачи элементов:

![](img/paging-example-1.png?p=plain&h=TVREC-274)

Приложение рассчитывает на то, что при следующем запросе множество не изменится, и на второй странице все выпуски телепередач будут новыми (идентификаторы 2, 1, 3, 5, 8).

Но при наличии постоянных изменений списка на сервере мы можем получить следующую картину:

![](img/paging-example-2.png?p=plain&h=TVREC-274)

В выборку добавились два выпуска (с идентификаторами 16 и 7), приложение вместо ожидаемых 5 новых выпусков получило дублирующееся описание выпусков с идентификаторами 9 и 11, и всего 3 новых элемента выборки. При удалении выпусков из выдачи также возможны пропуски при переходе на следующую страницу.

Решение данной проблемы заключается в передаче вместе со окном выдачи результатов двух дополнительных маркеров, отвечающих за получения "предыдущей" и "следующей" страницы: `lower_mark` и `upper_mark`, соответственно.

Для получения "следующей" страницы необходимо передать в качестве параметра `gt` значение `upper_mark`, а для получения "предыдущей" — в параметре `lt` значение `lower_mark`. В обоих случаях, в параметре `count` можно указать желаемое максимальное количество элементов выборки. Сервер может изменить данное количество для экономии сетевого трафика или для выдачи полной страницы выборки.

Полное количество выпусков телепередач, попавших в выборку (с учетом параметров `lt` и `gt`) сервер передает в поле `window_count`.

Рассмотрим, как именно это помогает решить проблему:

![](img/marking-example-1.png?p=plain&h=TVREC-274)

Получив первые результаты, приложение запоминает нижнюю и верхнюю границы выдачи, `lower_mark=100` и `upper_mark=150`, соответственно. Для получения "следующей" страницы приложение запрашивает выпуски с большим уровнем границы, чем `upper_mark`.

Рассмотрим случай получения "предыдущей" страницы:

![](img/marking-example-2.png?p=plain&h=TVREC-274)

Запомнив нижнюю границу, приложение запрашивает все результаты, имеющие уровень границы, меньший чем `lower_mark` имеющегося окна выборки. Для получения результатов, находящихся между двумя границами, необходимо указать оба параметра, `gt` и `lt`.

Замечания:

1. Названия `lower_mark` и `upper_mark` являются условными. Так, при сортировке выборки в убывающем порядке, значение `lower_mark` может быть большим или равным, чем значение `upper_mark`. Работа со значениями на стороне приложения в таком случае не меняется.
2. При смене рубрики или изменении значений опций рубрики в приложении должен производиться сброс всех известных значений нижних и верхних границ выборки.
3. На стороне сервера данная технология реализуется следующим образом:
	1. Выбирается поле результата выборки, по которому производится упорядочивание результатов выборки.
	2. Значения поля, по которому производится сортировка, должны быть достаточно дискретны. Различные страницы выборки должны содержать различные значения поля сортировки.
	3. Для сортировок по возрастанию в параметре `gt` передается нижняя, а в параметре `lt` — верхняя граница поля сортировки. Для сортировок по убыванию наоборот: в параметре `gt` передается верхняя, а в параметре `lt` — нижняя граница поля.
	4. Говоря другим языком, при сортировке по возрастанию выбранного на первом шаге поля, значение параметра `gt` должно использоваться для операции "строго больше", значение `lt` — "строго меньше". При сортировке по убыванию значение `gt` должно использоваться для операции "строго меньше", а `lt` — "строго больше".
	5. Поле `lower_mark` заполняется значением поля сортировки для первого элемента страницы выборки запроса, поле `upper_mark` — значением из последнего элемента страницы.
	6. Для упорядочения в рамках одной страницы рекомендуется использовать дополнительное поле, по которому производить сортировку, чтобы обеспечить одинаковое отображение одной и той же страницы на различных клиентах. В качестве второго поля можно использовать, к примеру, идентификаторы выпусков телепередач.

# Размещение и использование

Точка входа в веб–службы определяется [Регистратурой][registry-api-ref], при этом:

- TV Guide имеет числовой идентификатор `4`, строковый — `tv_guide`
- Peers.TV имеет числовой идентификатор `2`, строковый — `peerstv`

Запросы формируются следующим образом:

[registry-api-ref]: registry.md

	http://<path_to_api>/<method>.<format>?[parameters]

Где:

- `path_to_api` — путь до API, полученный из Регистратуры
- `method` — имя метода
- `format` — формат передачи данных, может быть одним из:
	- `.json` — JSON
	- `.xml` — XML
	- `.xspf` — XSPF (только для метода list)
	- `.png` — Portable Network Graphics, только для метода `logo` (<span style="color:#0f0">новое в 2.8</span>)
- `parameters` — параметры метода

Запрос к корневому URL API (без указания метода и формата) равносилен на запросу `list.xspf`.

# Возрастные ограничения

В версии TV API 2.1 введено понятие возрастного ограничения (возраст в годах, с которого можно потреблять медиа–контент без вреда для психики человека) для:

- выпуска телепередачи;
- телепередачи;
- канала.

Возрастные ограничения могут быть выставлены вручную или автоматически, на основании возрастных ограничений элементов, из которых состоит сущность. При автоматическом вычислении возрастного ограничения результат является максимумом возрастных ограничений элементов. Таким образом, для канала, возрастные ограничения телепередач которого колеблются от 0 до 18 лет, возрастным ограничением будет 18 лет.

## `idbytitle` — получение списка идентификаторов телеканалов по их именам [m-idbytitle]

Запрос идентификаторов каналов, для которых в плейлисте провайдера не использовано расширение `cn_id`.

 параметр | значение
----------|----------
`titles`  | Список названий телеканалов из плейлиста провайдера, для которых запрашиваются идентификаторы

Список названий телеканалов кодируются следующим образом:

1. Название канала передается в кодировке текста utf-8
2. Все запятые (`,`) в названии каналов экранируются символом `\`
3. Преобразованные названия склеиваются с помощью запятой (`,`)

Формат ответа: сообщение [`ChannelsList`][p-channelslist].

Замечания:

- Порядок каналов в ответе строго соответствует порядку каналов в запросе
- Для каждого запрошенного названия возвращается либо один идентификатор, либо ни одного
- Если для канала не было найдено подходящего идентификатора, но на соответствующей позиции *должно присутстовать пустое* сообщение `Channel`
- Если для канала был найден подходящий идентификатор, то в сообщении `Channel` должны заполняться поля:
	- `title` — название найденного телеканала
	- `channelId` — идентификатор найденного телеканала
- При поиске канала по названию сервер:
	- производит регистронезависимый поиск по названию канала
	- производит замену символов `е` и `ё` при необходимости
	- производит замену символов табуляции и переноса строки на символ пробела
	- удаляет лишние пробелы в названии (лидирующие, хвостовые и идущие подряд несколько раз)

## `rubricator` — получение рубрикатора (<span style="color:#0f0">новое в 2.8</span>) [m-rubricator]

Дополнительные параметры:

 параметр     | формат    | по умолчанию | смысл
--------------|-----------|--------------|-------
`rubric`      | `число`   | отсутствует  | Идентификатор рубрики, для которой запрашиваются подрубрики
`quantity`    | `число`   | отсутствует  | Максимальное количество подрубрик в выдаче

Способ кодирования параметров `rubric` и `rubric_options` описан в параграфе "[Передача значений выбранных опций рубрик][para-rubric-options-encoding]".

За сервером остается право ограничивать размер ответа. Для этого вместо выдачи полного дерева рубрик могут быть использованы следующие техники:

- передача поля наличия подрубрик `have_subitems` вместо передачи непосредственно списка подрубрик в поле `subitems`. Для получения подрубрик в таком случае необходимо сделать еще один запрос получения рубрикатора, передав идентификатор вышестоящей рубрики в параметре `rubric`.
- передача неполного списка подрубрик. В таком случае в ответе передается дополнительное поле `total_count`, содержащее точное значение количества подрубрик. Клиент должен сделать дополнительные запросы, указывая параметр смещения `skip`.
- Клиент может передать желаемое количество подрубрик в параметре `quantity`, однако за сервером остается право уменьшить данное значение на своей стороне.

## `logo` — Запрос логотипа для рубрики (<span style="color:#0f0">новое в 2.8</span>) [m-logo]

 параметр     | формат         | по умолчанию | смысл
--------------|----------------|--------------|-------
`rubric`      | `число`        | отсутствует  | Идентификатор рубрики
Представление данных ||||
`profile`     | `строка`       | `web`        | желаемый профиль изображения
`strict`      | `true`, `false`| `false`      | возращать логотип только при точном соотвествии параметров представления

Для логотипов элементов медиа–каталога может существовать несколько профилей отображения, адаптированных под дизайн или возможности платформы. - `web` — адаптированный для отображения в вебе;
- `android` — адаптированный для устройств на базе Android;
- `ios` — адаптированный для устройств на базе iOS.

Также можно указать желаемые размеры логотипов при помощи параметров `resolution`, если данный параметр указан, то сервер вернет наиболее близкое по размеру изображения, но не меньше запрашиваемого, если подходящего изображения не найдено, то будет возвращено изображение по умолчанию.

При указании параметра `strict` со значением `true` сервер должен вернуть HTTP код `404` с пустым телом ответа, если логотип с запрашиваемыми параметрами представления не найден.

Признак наличия записей для канала определяется в соответствии с типом записей и устройством, определенным по HTTP–заголовку User-Agent или переданным при помощи параметра `device`. В остальных случаях признак записей устанавливается, только если существуют записи поддерживаемого устройством типа. Так, например, SmartTV Samsung серий C и D не поддерживает записи в формате HLS.

# История версий

## Изменения в версии 2.0

1. Изменения в общих параметрах:
	- Убран `ao` — за ненадобностью;
	- Убран `uid` — должен передаваться на сервер статистики, а не в API;
	- Убран параметр `tz` — данные берутся из описания территории.
2. В XSPF оставлен только один метод — list.xspf, для клиентов, не поддерживающих API. Все остальное переведено на JSON, XML и Protocol Buffers.
3. Убран метод договора оферты.
4. Убран метод получения дат с наличествующем расписанием для канала.
5. Добавлен метод получения описания о конкретном канале.
6. Добавлен метод получения информации о канале по идентификатору выпуска телепередачи.
7. Добавлена возможность получения расписания передач канала для нескольких дат.

## Изменения в версии 2.1

1. Добавлен признак доступности эфира и записей телепередач канала.
2. Метод `/list` помечен как "устаревший". В версии 3.0 TV API данного метода *не будет*.
3. Добавлена сущность "Телепередача".
4. В информацию о выпуске телепередачи добавлен канал, на котором был выпуск.
5. Добавлены параметры "Возрастные ограничения" для канала, передачи и выпуска телепередачи.
6. Добавлен параметр наличия расписания в сообщении `Channel`.

## Изменения в версии 2.2

1. Указан ориентир на [Catalogue API][catalogue-api-ref]
2. Добавлен метод получения предполагаемых идентификаторов каналов по их написанию `idbytitle`


## Изменения в версии 2.3

1. Добавлен метод получения топ передач за указанный период времени (Closes: #WEBDEV-6465)
2. В сообщение `Schedule` добавлены поля `items_skipped` и `total_count`, отвечающие за частичную выдачу информации
3. В сообщение `Telecast` добавлено поле `views_count`, отвечающее за количество просмотров выпуска телепередачи пользователями сервиса

## Изменения в версии 2.3.1

1. Уточнено использование API в рамках веб–служб TV Guide и Peers.TV
2. Поле `access` для канала помечено устаревшим

## Изменения в версии 2.4

1. Добавлен атрибут `storage_hours` для канала, отражающий время хранения записей выпусков телепередач на серверах сервиса Peers.TV

## Изменения в версии 2.5

1. Обновлена дата планового срока внедрения Catalogue API;
