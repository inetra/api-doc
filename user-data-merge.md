О чем данный документ
==================

Данный документ описывает API слияния учеток двух пользователей в одну.

Виды пользователей описаны в документах [История просмотра: варианты использования][ВИ История] и [Auth API], могут быть двух видов:

- с паспортом CN.ru
- анонимные

[Auth API]: auth.md
[ВИ История]: http://drug/iwiki/pages/viewpage.action?pageId=4063632

В первой версии API возможны слияния только двух пользователей, при этом хотя бы один из них должен быть анонимным.

Слияние пользователей — суть слияние их деревьев данных. Алгоритм слияния описан в приложении к User Data API.

Общее описание
=============

API работает по протоколу HTTPS для сокрытия передаваемых данных. Запросы составляются следующим образом:

	https://<path_to_api>/<method>.<format>?[extra_data]

Где:

- `path_to_api` — путь до API, полученный из Регистратуры
- `method` — название метода
- `format` — формат кодирования данных в теле запроса и ответа
- `extra_data` — дополнительные параметры метода.

Формат кодирования данных может быть одним из двух:

- `json` — JSON;
- `protobuf` — Protocol Buffers.

Методы
======

users_merge — слияние пользователей
-----------------------------------

Дополнительные параметры:

параметр       | значение по умолчанию  |	смысл 
---------------|------------------------| ----- 
`mine_token`   | отсутствует            | токен доступа пользователя, которой производит слияние
`their_token`  | отсутствует            | временный токен доступа пользователя, который запросил слияние
`resolve_hint` | пусто                  | подсказка, в чью пользу разрешать конфликты слияния данных


Подсказка для разрешения конфликтов может принимать одно из двух значений: `mine` или `their`. Если подсказка отсутствует, сервер отдает предпочтение данным пользователя с Паспортом, т.е. не анонимному.

Возможные коды ответов:

код | значение
----|---------
200 | успешное слияние
401 | неверный токен доступа пользователя, производившего слияние
403 | неверный временный токен доступа пользователя, запросившего слияние
409 | обнаружены конфликты слияния данных

Формат ответа: сообщение `MergeConflicts`.

При обнаружении конфликтов слияния приложение, производившее слияние данных, должно отобразить пользователю список конфликтующих данных и их атрибутов (возможно, в преобразованном виде) и после принятия решения пользователем произвести изменения в данных соответствующего пользователя с помощью User Data API, после чего повторить операцию слияния до полного разрешения конфликтов.

Формат данных
=============

MergeConflicts — конфликты слияния
----------------------------------

	message MergeConflict {
	  optional string element_path = 1;
	  optional bytes mine_attributes = 2;
	  optional bytes their_attributes = 3;
	}
	 
	message MergeConflicts {
	  repeated MergeConflict conflicts = 1;
	}

Рекомендации по реализации слияния данных двух пользователей
============================================================

При слиянии данных пользователей они должны быть объединены в единое дерево, при этом всегда есть пользователь–источник данных и пользователь–получатель, а слияние данных — суть слияние корневого элемента пользователя–источника в корневой элемент пользователя–получателя:

	function merge_users(dst, src) {
	  merge_elements(dst.root, src.root);
	}

Алгоритм слияния элементов может быть следующим:

1. Если множество классов элемента–получателя не совпадают с множеством классов элемента–источника, завершиться с ошибкой.
2. Произвести слияние атрибутов.
3. Для каждого дочернего элемента в источнике:
	* Если элемент с таким идентификатором отсутствует в элементе–получателе, то скопировать дочерний элемент в элемент–получатель, сохранив его идентификатор.
	* Иначе,
		* Если идентификатор дочернего элемента в источнике является автоматически сгенерированным,
			1. Сгенерировать новый элемент в получателе с идентификатором `new_name`;
			2. Скопировать дочерний элемент в новый элемент `new_name`;
			3. Сохранить `new_name` в качестве идентификатора нового элемента.
		* Иначе, если идентификатор дочернего элемента в получателе является автоматически сгенерированным,
			1. Сгенерировать новый элемент в получателе с идентификатором `new_name`;
			2. Переместить дочерний элемент получателя в новый элемент `new_name`;
			3. Сохранить `new_name` в качестве идентификатора нового элемента;
			4. Скопировать дочерний элемент источника в получатель.
		* Иначе, произвести алгоритм слияния одноименных дочерних элементов из источника в получатель.

Пример реализации алгоритма на псевдоязыке:

	function merge_elements(dst, src) {
	  if (dst.class_name != src.class_name) {
	    return;
	  }
	  dst.attributes.merge(src.attributes);
	 
	  for (child in src.children) {
	    var new_name;
	    if (!(child.id in dst)) {
	       dst[child.id] = child;
	    } else {
	      if (child.id_autogenerated) {
	         new_name = dst.generate_id();
	         dst[new_name] = child;
	         dst[new_name].id = new_name;
	      } elif (dst[child.name].id_autogenerated) {
	         new_name = dst.generate_id();
	         dst[new_name] = dst[child.id];
	         dst[new_name].id = new_name;
	         dst[child.id] = child;
	      } else {
	         merge_elements(dst[child.id], child);
	      }
	    }
	  }
	}
