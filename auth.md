# Цель и смысл

Данный документ описывает реализацию аутентификации пользователей и авторизации приложений.

Варианты использования, приводящие к данному API, описаны на странице [вариантов использования истории просмотра][browsing-history-use-cases].

[browsing-history-use-cases]: http://drug/iwiki/pages/viewpage.action?pageId=4063632

В версии 1.0 данное API представляет собой протокол [OAuth 2.0 Framework]. На первых порах будет достаточно реализации передачи логина/пароля в открытом виде, так как пользоваться будут только доверенные приложения Инетры.

[OAuth 2.0 Framework]: http://tools.ietf.org/html/rfc6749

# Предметная область

## Пользователь

Пользователи разделены на две группы:

- анонимные, без владения паролем. В качестве логина такого пользователя обычно выступает автоматически сгенерированный идентификатор пользователя[^fn-several-ids].
- с «паспортом», например, паспортом CN.ru[^fn-cnru-passport], владеющие паролем. В качестве логина и пароля пользователя фигурируют логин и пароль Паспорта CN.ru, соответственно.

## Токен

Соответственно, токены доступа могут быть двух видов:

- анонимные (у анонимных пользователей);
- персональные (у пользователей с Паспортом).

После получения, токен доступа живет ограниченное время, указанное в ответе. На стороне клиента необходимо реализовывать обработку ошибки просроченного токена и получать новый токен доступа.

## PIN-код

Также отдельным Flow реализован запрос цифрового PIN–кода переменной длины, от 4 до 20 знаков, рекомендуется длиной в 6[^fn-pin-notes] знаков, который живет короткое время, рекомендуется 15 минут[^fn-pin-notes]. Аутентифицированный пользователь (в том числе, анонимный) с помощью такого временного токена доступа имеет возможность аутентификации на другом устройстве без ввода логина/пароля.

[^fn-several-ids]: Важно разделять идентификаторы пользователя (user_id), приложения (appinstance_id) и устройства (device_id). Такое разделение позволит правильно обрабатывает любые кейсы, описанные в [вариантах использования истории просмотра][browsing-history-use-cases], например.

[^fn-cnru-passport]: Замечание: Использование именно паспорта CN.ru принято для ускорения запуска продукта Peers.TV. Планируется разработка собственного отдельного сервиса AAA для продуктов Инетры. Рекомендую использовать более обобщённые упоминания паспортной системы.

[^fn-pin-notes]: Длина PIN-кода выбирается как баланс между простотой и безопасностью. Альфа-Банку хватает 6-ти символов для подтверждения банковских операций.

# Взаимодействие с API

Расположение данного API фиксировано: `https://api.cn.ru/auth[.json]/[$MAJOR_VERSION/]` (внимание: доступно только по HTTPS). Сервис API должен присутствовать в Регистратуре в списке сервисов, предоставляемых Инетрой.

Параметры к запросам передаются методом GET, их значения экранируются стандартным URI кодированием. Таким образом, обращение к API строится по схеме:

	https://api.cn.ru/auth/1/<method>?[param1=value1& ... paramN=valueN]

Где `<method>` — имя метода (например, `UserCredentials` или `PidCode`), а `param1`, `paramN` — параметры.

Формат ответов всегда JSON.


# Методы

## UserCredentials — получение токена доступа

Реализован OAuth 2.0 Flow: Resource Owner Password Credentials Grant.

### Параметры для аутентификации пользователя по логину с паролем

Все параметры являются обязательными[^fn-client_id_notes].

 параметр       | значение
----------------|----------
`grant_type`    | должно быть `password`
`client_id`     | идентификатор клиента
`client_secret` | разделяемый секрет клиента
`login`         | логин пользователя
`password`      | пароль пользователя

### Параметры для аутентификации анонимного пользователя

Все параметры являются обязательными[^fn-client_id_notes].

 параметр       | значение
----------------|----------
`grant_type`    | должно быть `anonymous`
`client_id`     | идентификатор клиента
`client_secret` | разделяемый секрет клиента
`uid`           | идентификатор установки приложения

### Формат ответа

	message TokenReply {
	  optional string access_token = 1;
	  optional string token_type = 2;
	  optional int32 expires_in = 3;
	  optional string error = 4;
	  optional string error_description = 5;
	}

Замечания:

- `access_token` — токен доступа
- `token_type` — зарезервировано, на данный момент всегда возвращается `example`
- `expires_in` — время жизни полученного токена доступа, в секундах относительно времени запроса
- `error` — строковая константа, описывающая случившуюся ошибку
- `error_description` — строка с сообщением, которое можно показать пользователю (если есть)

HTTP код ответа может быть:

- `200` — успешная аутентификация, в таком случае возвращаются поля `access_token`, `token_type` и `expires_in`,
- `400` — отказ в аутентификации, в теле ответа содержится только поле `error`[^fn-error-codes]

[^fn-client_id-notes]: рекомендую изменить ключевое слово client, как слишком многозначное, и использовать предложенные ключевые слова user_id, appinstance_id, device_id. В данном случае – user_id. Для совместимости в пределах версии 1 можно использовать синонимы.

[^fn-error-codes]: Предлагаю использовать унифицированный список кодов ответов (ошибок) из стандарта [HTTP/1.1], для бОльшей однозначности, он привычен и широко используется. Отказу в аутентификации соответствует 401 (неавторизован, рекомендован повторный запрос с challenge) или 403 (отказано окончательно, не спрашивай больше).

[HTTP/1.1]: http://www.w3.org/Protocols/rfc2616/rfc2616-sec10.html

### Возможные ошибки

 строковая константа    | описание ошибки
------------------------|-----------------
`invalid_request`       | неправильный запрос, ошибочный параметры, или параметры неправильныя для данного `grant_type`
`invalid_client`        | неизвестный `client_id`, неразрешенный `grand_type` для данного клиента, неверное значение `client_secret`
`invalid_grant`         | неверная пара логин/пароль
`unauthorized_client`   | клиент неавторизован для данного `grant_type`
`unsupported_grant_type`| неизвестное значение параметра `grant_type`

### Пример успешного взаимодействия

Запрос

	GET /auth/UserCredentials?grant_type=anonymous&client_id=91801674-777e-4edd-aacc-1911c7262115&client_secret=3WzahKEFZqhm3GpowLAsS4&uid=8911215c-04b9-46f8-a2af-6116b7e352f1 HTTP/1.1
	Host: api.cn.ru

Ответ

	HTTP/1.1 200 OK
	Content-Type: application/json;charset=UTF-8
	
	{
	  "access_token":"2YotnFZFEjr1zCsicMWpAA",
	  "token_type":"example",
	  "expires_in":3600  
	}

## PinCode — получение PIN кода

Параметром для данного метода является `token` — токен доступа, полученный приложением на первом этапе.

В случае, если передан некорректный токен доступа, сервер возвращает ошибку `403 Forbidden`.

### Формат ответа

	message PinCodeReply {
	  optional string pin = 1;
	  optional int32 expires_in = 2;
	}

Замечания:

- `pin` — PIN код, отображаемый пользователю
- `expires_in` — время жизни PIN кода, в секундах относительно создания

### Пример успешного взаимодействия

Запрос

	GET /auth/PinCode?token=2YotnFZFEjr1zCsicMWpAA HTTP/1.1
	Host: api.cn.ru

Ответ

    HTTP/1.1 200 OK
    Content-Type: application/json;charset=UTF-8
    Cache-Control: no-store
    Pragma: no-cache

    {
      "pin": "012345678",
      "expires_in": 600  
    }
