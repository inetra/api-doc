# Цель и смысл

Данный документ описывает реализацию аутентификации пользователей и авторизации приложений.

Варианты использования, приводящие к данному API, описаны на странице [вариантов использования истории просмотра][browsing-history-use-cases].

[browsing-history-use-cases]: http://drug/iwiki/pages/viewpage.action?pageId=4063632

Auth API реализует протокол авторизации в соответствии с [OAuth 2.0 Framework]. На первых порах будет достаточно реализации передачи логина/пароля в открытом виде, так как в качестве клиентов будут выступать только доверенные приложения Инетры.

[OAuth 2.0 Framework]: http://tools.ietf.org/html/rfc6749

# Предметная область

## Пользователь

Пользователи разделены на две группы:

- анонимные, без владения логином и паролем.
- не анонимные, владеющие логином и паролем. Пользователь знает и логин, и пароль, для аутентификации ему нужно ввести оба значения в специальные поля в интерфейсе приложения. 

## Токен доступа

Токены доступа могут быть двух видов:

- анонимный (принадлежащий анонимному пользователю);
- персональный (принадлежащий не анонимному пользователю).

После получения токен доступа действует ограниченное время, указанное в ответе. На стороне клиента необходимо реализовывать обработку ошибки просроченного токена и получать новый токен доступа. Токен доступа также характеризуется типом, указывающим на схему авторизации, которую должен использовать клиент.

## PIN-код

Отдельно реализован запрос цифрового PIN–кода переменной длины, от 6 до 15 знаков (рекомендуемая длина 9[^fn-pin-length] знаков), который живет короткое время (рекомендуемое время жизни 15 минут). Аутентифицированный пользователь (в том числе, анонимный) с помощью такого временного токена доступа имеет возможность аутентификации на другом устройстве без необходимости ввода дополнительной информации.

[^fn-pin-length]: Длина PIN-кода выбирается как баланс между простотой и безопасностью. Альфа-Банку хватает 6-ти символов для подтверждения банковских операций.

# Получение идентификатора и секретного ключа клиента

Каждое авторизующееся приложение должно иметь свой идентификатор и секретный ключ, которые в дальнейшем используются в методах данного API в параметрах `client_id` и `client_secret`, соответственно.

На данный момент получение данных значений возможно с помощью службы технической поддержки компании Инетра (support@inetra.ru) с предоставлением дополнительных данных:

- аккаунт разработчика приложения на сайте CN.ru или Peers.TV
- название приложения
- логотип приложения

# Аутентификация при помощи токена доступа

Клиент *должен* выполнять аутентификацию в соответствии с типом выданного токена доступа. Для аутентификации по типу токена "[Bearer][rfc6750]" рекомендуется использовать HTTP заголовок `Authorization`, пример:

	Authorization: Bearer 18dasd81230dah12032

[rfc6750]: http://tools.ietf.org/html/rfc6750

# Авторизация при помощи другого авторизованного приложения

Приложение может осуществить авторизацию при помощи другого авторизованного приложения. Для этого авторизующееся приложение должно получить код устройства и PIN–код (см. метод [`DeviceCode`][m-device-code]). Авторизующееся приложение *должно* отобразить полученный PIN–код в графическом интерфейсе и предложить пользователю ввести PIN–код в другом авторизованном приложении.

После ввода PIN–кода пользователем авторизованное приложение должно подтвердить авторизацию (см. метод [`ConfirmCode`][m-confirm-code]), в это время авторизующееся приложение *должно* периодически проверять завершение процесса авторизации (см. метод [`UserCredentials`][m-user-credentials])

# Взаимодействие с API

Расположение данного API фиксировано: `https://api.cn.ru/auth/<version>/` (внимание: доступно только по HTTPS). Сервис API должен присутствовать в Регистратуре в списке сервисов, предоставляемых Инетрой.

Параметры к запросам передаются методом GET, их значения экранируются стандартным URI кодированием. Таким образом, обращение к API строится по схеме:

	https://api.cn.ru/auth/1/<method>?[<parameters>]

Где:

- `<method>` — имя метода (например, `UserCredentials` или `PidCode`)
- `<parameters>` — параметры метода

Формат ответов всегда JSON.

Значения всех параметров перед передачей серверу необходимо кодировать для предотвращения неоднозначной интерпретации так, как это рекомендуется в [RFC3986].

[RFC3986]: http://tools.ietf.org/html/rfc3986

## Аутентификация

Для метода `UserCredentials` параметры аутентификации передаются только при помощи параметров метода.

Для остальных методов — для аутентификации пользователя клиент должен передать полученный ранее токен доступа, выданный службой контрагента, реализующей [Auth API][auth-api-doc], по схеме аутентификации в соответствии с типом токена.

[auth-api-doc]: auth.md

## Стандартные коды ответов

Для каждого метода API предусмотрены стандартные коды ответов ([RFC2616][rfc2616]). Ниже описана интерпретация некоторых кодов:

- `200` — запрос успешно обработан
- `400` — некорректно составлен запрос
- `401` — требуется аутентификация:
	- необходимо передать данные аутентификации;
	- данные аутентификации некорректны;
	- данные аутентификации корректны, но переданный токен доступа был отозван или истек срок его действия.
- `403` — доступ запрещен:
	- переданы данные аутентификации, которые не позволяют выполнить запрос в силу отсутствия необходимых разрешений;
	- аутентификация невозможна, например, закрыт доступ по IP адресу.

### Для методов `PinCode`, `ConfirmCode`:

Если аутентификация возможна, то для кодов `401`, `403` *должен* быть передан HTTP заголовок `WWW-Authenticate` с указанием ожидаемой схемы аутентификации и дополнительнной информации (если применимо). Например, для схемы ["Bearer"][rfc6750] *может* быть указан дополнительный атрибут `error` со значением:

- `invalid_token` — передан некорректный, просроченный или отозванный токен доступа (код `401`);
- `insufficient_scope` — запрос требует более высоких привилегий, чем те, которыми обладает токен доступа (код `403`).

# Методы

## UserCredentials — получение токена доступа [m-user-credentials]

Реализован OAuth 2.0 Flow: Resource Owner Password Credentials Grant.

Основные параметры для аутентификации:

 параметр       | значение
----------------|----------
`grant_type`    | тип аутентификации
`client_id`     | идентификатор клиента
`client_secret` | разделяемый секрет клиента

Формат ответа: [`TokenReply`][p-token-reply]

Возможные значения для параметра `grant_type`:

- `anonymous` — анонимная аутентификация, дополнительные параметры не требуются.
- `password` — аутентификация по логину/паролю пользователя;
- `device_code` — аутентификация при помощи другого авторизованного приложения;
- `renew` — возобновления токена доступа.

> TODO "device_code" — по https://tools.ietf.org/html/rfc6749 незарегистированная схема должна быть задана с использованием URI

Дополнительные параметры (в зависимости от типа аутентификации):

 параметр       | значение
----------------|----------
Тип аутентификации `password` ||
`login`         | логин пользователя
`password`      | пароль пользователя
Тип аутентификации `renew` ||
`access_token`  | просроченный токен доступа
`renew_token`   | токен возобновления доступа
Тип аутентификации `device_code` ||
`code`          | код, выданный для устройства (см. метод [DeviceCode][m-device-code])

Все параметры являются обязательными.

При успешном выполнении операции будет передан токен доступа с указанием схемы аутентификации.

При восстановлении токена доступа будет выдан новый токен доступа, токен для возобновления доступа может быть обновлен.

**ВАЖНО**: на время переходного периода (до декабря 2015) будут действовать следующие правила:

- если клиент не выполнял ранее процедуру возобновления токена доступа (владеет бессрочным токеном, не владеет токеном возобновления), то допускается не передавать параметр `renew_token` при возобновлении токена доступа;
- существующие клиенты, продолжающие передавать "uid" для анонимной аутентификации, будут получать бессрочный токен доступа:
	- при прочих условиях получения и возобновления будет выдан токен доступа с ограниченным сроком действия;
- после возобновления токена доступа, переданный токен должен быть помечен как неактивный;
- операция возобновления токена доступа применима только к последнему и предпоследнему токенам доступа.

### Возможные ошибки

 строковая константа    | описание ошибки
------------------------|-----------------
`invalid_request`       | неправильный запрос, ошибочный параметры или некорректные параметры для данного `grant_type`
`invalid_client`        | неизвестный `client_id`, неразрешенный `grant_type` для данного клиента, неверное значение `client_secret`
`invalid_grant`         | неверная пара логин/пароль или код устройства
`unauthorized_client`   | клиент неавторизован для данного `grant_type`
`unsupported_grant_type`| неизвестное значение параметра `grant_type`
`waiting_authorization` | ожидание авторизации, актуально для `grant_type` со значением `device_code`

Если авторизация приложения для анонимного пользователя запрещена (возвращена ошибка `unauthorized_client`),  то клиент должен запросить логин и пароль пользователя для получения доступа на основе не анонимной авторизации.

# Устаревшие методы

## PinCode — получение PIN кода (<span style="color:#f00"> устарело с версии 1.5.0</span>)

Основные параметры:

 параметр | значение
----------|----------
`token`   | токен доступа, полученный приложением при помощи Auth API. (<span style="color:#f00">устарело с версии 1.4.0</span>)
`purpose` | назначение для PIN кода

Формат ответа: [`PinCodeReply`][p-pin-code-reply]

Возможные значения параметра `purpose`:

- `authenticate` — идентификация и аутентификация пользователя;
- `confirm` — подтверждение операции посредством PIN кода.

Для назначения `authenticate` выданный токен должен быть уникальным среди всех пользователей в рамках срока его действия и дополнительного защитного интервала. Выданный PIN код может быть использован для операции объединения учетных записей [UserDataMerge][user-data-merge-doc]. 

Для назначения `confirm` выданный токен должен быть уникальным для пользователя в рамках срока его действия.

Замечание по реализации: во избежание коллизий не рекомендуется отображать PIN код после истечения срока действия.

[user-data-merge-doc]: user-data-merge.md

# Спецификация API для Protocol Buffers

## `TokenReply` — получение токена доступа [p-token-reply]

	message TokenReply {
	  optional string access_token = 1;
	  optional string token_type = 2;
	  optional string renew_token = 6;
	  optional int32 expires_in = 3;
	  optional string error = 4;
	  optional string error_description = 5;
	}

Замечания:

- `access_token` — токен доступа
- `token_type` — тип токена, который задает схему аутентификации, возможные типы:
	- `bearer` — тип токена "[Bearer][rfc6750]".
- `renew_token` — токен возобновления доступа, необходимый для получения нового токена доступа. Срок жизни не ограничен, но может быть обновлен при получении нового токена доступа;
- `expires_in` — время жизни полученного токена доступа, в секундах относительно времени запроса
- `error` — строковая константа, описывающая случившуюся ошибку
- `error_description` — строка с сообщением, которое можно показать пользователю (если есть)

В случае успешной аутентификации *должны* быть возвращены атрибуты `access_token`, `renew_token`, `token_type` и `expires_in`.
В случае ошибки — в теле ответа содержится атрибут `error` и `error_description`.

## `DeviceCode` — получение кода устройства [p-device-code]

	message DeviceCode {
	  optional string pin = 1;
	  optional string device_code = 2;
	  optional int32 expires_in = 3;
	  optional int32 interval = 4;
	}

Замечания:

- `pin` — PIN код, отображаемый в графическом интерфейсе, для ввода пользователем в другом приложении;
- `device_code` — код устройства для получения токена доступа после завершения авторизации в другом авторизованном приложении;
- `expires_in` — срок жизни выданных кодов (в секундах);
- `interval` — интервал для проверки авторизации по коду устройства.

## `PinCodeReply` — получение PIN–кода [p-pin-code-reply]

	message PinCodeReply {
	  optional string pin = 1;
	  optional int32 expires_in = 2;
	}

Замечания:

- `pin` — PIN код, отображаемый пользователю
- `expires_in` — время жизни PIN кода, в секундах относительно создания
