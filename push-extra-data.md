# Общее описание

Данный документ описывает способ задания дополнительной информации в полезной нагрузке push–уведомления. 

Дополнительная информация может быть использована приложением для выполнения тех или иных действий при переходе по push–уведомлению в приложение, например, открытие расписания заданного телеканала.

Поддерживаемые платформы:

- Apple iOS;
- Google Android.

С целью задействовать специфичные особенности каждой из поддерживаемых платформ список поддерживаемых действий может различаться.

# Описание дополнительной информации

Для однозначного интерпретирования назначения дополнительных параметров в полезной нагрузке push–уведомления вводится понятие `тип события`. Тип события описывает назначение параметров, переданных в полезной нагрузке push–уведомления.

Известные типы событий:

тип | смысл
----|------------
`0` | Зарезервировано. Редакционное сообщение
`1` | Новый канал, рекомендация канала пользователям
`2` | Уведомление о выпуске телепередачи
`3` | Доступно новое обновление приложения
`4` | Рекомендация раздела "Популярные телепередачи"
`5` | Рекомендация одного из разделов "Тематической подборки"
`6` | Интернет-ресурс
`7` | Уведомление о выходе выпуска телепередачи в эфир

В случае редакционного сообщения указывать тип сообщения **не нужно**.

Замечание: список известных событий будет расширяться по мере необходимости. Крайне не рекомендуется использовать одно событие для логически разных реакций приложения.

Для каждого типа события заранее известен набор обязательных параметров.

Сущности канал, передача, выпуск телепередачи разделяют одно пространство идентификаторов, поэтому, для простоты, далее вместо упомянутых сущностей будем использовать понятие `элемент каталога`, по необходимости внося уточнения о типе каталога.

Перечень возможных параметров для каждого типа события:

тип |   параметр    | значение | смысл параметра
----|---------------|----------|---------------
`1` | `catalogItem` | `число`  | Идентификатор канала
`2` | `catalogItem` | `число`  | Идентификатор выпуска передачи
`5` | `collection`  | `число`  | Идентификатор тематической коллекции
`6` | `url`         | `строка` | Ссылка на интернет ресурс. Рекомендуется использовать shortener-сервисы.
`7` | `catalogItem` | `число`  | Идентификатор выпуска передачи

Замечание: обязательные параметры для типа события отсутствуют, если не указаны в сводной таблице.

## Возможные реакции приложения на события

Каждый тип события может быть обработан особым образом. Данные сценарии могут измениться и несут только ознакомительный характер. Сценарии применимы только к клиентским приложениям.

- **Событие `1` — Рекомендация канала**. Приложение может открыть эфир канала, расписание для канала или выполнить любое другое действие по маркированию канала списке каналов (например, добавить иконку "New").

- **Событие `2` — Уведомление о выпуске телепередачи**. Приложение должно перейти на экран телепередачи и запустить проигрывание.

- **Событие `3` — Доступно новое обновление приложения**. Приложение должно перейти в Apple App Store или Google Play Market на страницу обновления приложения.

- **Событие `4` — Рекомендация раздела "Популярные телепередачи"**. Приложение должно открыть раздел "Популярные телепередачи" с выбранной рубрикой за неделю.

- **Событие `5` — Рекомендация одного из разделов "Тематической подборки"**. Приложение должно открыть одну из тематических подборок.

- **Событие `6` — Интернет-ресурс**. Приложение может открыть в внешнем или во внутреннем браузере (по отношению к приложению) ссылку, указанную в дополнительных параметрах.

- **Событие `7` — Уведомление о выходе выпуска телепередачи в эфир**. Приложение должно открыть указанную передачу для просмотра в эфире.

## Отслеживание эффективности push–уведомлений

Для отслеживания эффективности push–уведомлений(количество переходов по действию) необходимо указывать в дополнительных параметрах идентификатор рассылки `pdid`(Push delivery ID). Выполнив переход по push–уведомлению, клиентское приложение *должно* отправить на сервер статистики соответствующее событие.

## Регламент сопровождения данного документа

Перечень событий, описанный выше, может только дополняться. Конкретные события, их параметры не могут быть изменены, в случае подобной необходимости должны быть созданы и описаны новые события.

# Способ задания дополнительной информации

В зависимости от платформы способ формирования запросов и задания дополнительных параметров может отличаться.

Общая схема работы:

- сервер формирует и отправляет запрос к шлюзу доставки push–уведомлений;
- приложение получает и анализирует основные и дополнительные параметры push–уведомления, выполняя необходимые действия.

## Платформа Android

Основные и дополнительные параметры указываются в элементе `data` запроса к GCM шлюзу. После получения push–уведомления клиентскому приложению доступны пары "ключ" – "значение" из элемента `data`, переданного в запросе. Все параметры находятся на одном уровне.

Основные параметры не подлежат изменению, но список может быть расширен. Основные параметры должны обладать префиксом 'gcm_'.

Перечень основных параметров:

название      | значение | смысл
--------------|----------|---------
`gcm_title`   | `строка` | Заголовок сообщения[^fn-title]
`gcm_message` | `строка` | Текст сообщения

[^fn-title]: Заголовок сообщения может использоваться в заголовке диалогового окна.

**Примеры сообщений для GCM шлюза:**

Уведомление о новом выпуске телепередачи

	{
		"data": {
			"gcm_title": "Передача записана",
			"gcm_message": "Мы записали для вас новый выпуск вашей любимой передачи \"Язь против еды\"",

			"pdid": 123,
			"type": 3,
			"catalogItem": 120394723
		},
		
		"registration_ids": ["4","8","15","16","23","42"]
	}
	
Уведомление о наличии обновления

	{
		"data": {
			"gcm_title": "Новое обновление",
			"gcm_message": "Доступно новое обновление!",

			"pdid": 124,
			"type": 1
		},

		"registration_ids":["4","8","15","16","42"]
	}


## Платформа iOS

Основные параметры задаются в элементе `aps`, дополнительные — на верхнем уровне сообщения.
Перечень основных параметров описан в [официальной][apns-doc-link] документации от Apple.

Платформа iOS вносит существенные ограничения на размер полезной нагрузки всего push–уведомления, на данной момент эта величина составляет 256 байт с учетом активной, используемой ОС, и пассивной нагрузки.

Таким образом для текстового сообщения за вычетом дополнительных параметров остается около 200 байт. В случае использования кириллицы длина сообщения может составлять до 100 символов.

[apns-doc-link]: https://developer.apple.com/library/ios/documentation/NetworkingInternet/Conceptual/RemoteNotificationsPG/Introduction.html

**Примеры сообщений для APNS шлюза:**

Уведомление о новом выпуске телепередачи 

	{
		"aps": {
			"alert" : "We've recorded an amazing telecast special for you."
		},

		"pdid": 123,
		"type": 3,
		"catalogItem": 120394723
	}

Уведомление о наличии обновления
	
	{
		"aps": {
			"alert" : "Please check for new updates!"
		},

		"pdid": 124,
		"type": 1
	}

# История изменений

## Изменение в версии 0.6:

- Для платформы Андройд элемент `gcm` при указании основных параметров заменен на префикс `gcm_`.

## Изменение в версии 0.7:

- Добавлены описания событий `0` и `7` — редакционное уведомление, уведомление о выходе в эфир выпуска телепередачи.

## Изменение в версии 0.8:

- Описана реакция приложения на событие `7`.

## Изменение в версии 0.9:

- Описан регламент сопровождения данной документации.
